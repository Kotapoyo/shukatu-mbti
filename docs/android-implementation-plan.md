# Androidアプリ作成計画

> 2026年11月1日更新: 開発用の学生プロフィール全項目について、本人限定のJSON API、MySQL保存、Android入力画面を実装しました。APIテストは成功し、Androidは実装直後のビルドが成功しました。レビュー修正後の再ビルドは実行環境のSDK参照権限で停止しました。Web画面のブラウザー保存データはAPIへ自動移行されません。プロフィール画面での保存操作はエミュレーターで未確認です。

- 作成日：2026年11月1日
- 状態：当初計画と進捗。架空データ用のAndroid・JSON APIは実装中
- 対象：`docs/requirements.md` の初期開発範囲（FR-01〜FR-09、NFR-01〜NFR-03）

## 1. 目的と前提

学生がAndroid端末でログインし、プロフィールと希望条件の登録、診断、提案結果、企業詳細、保存企業の確認を行えるようにする。企業情報登録は要件に含まれるが、企業アカウントの承認・権限が未確定なので、その仕様が決まるまで実在企業向けの機能として公開しない。開発・デモには架空データだけを使う。

Web版を先に完成させ、その後Android版を作る方針を維持する。Android版はWeb版と同じサーバーのJSON APIを利用し、端末からMySQLへ直接接続しない。診断の採点・候補選定をAndroid側に複製しない。

## 2. 着手前に確認した差分

| 項目 | 現状 | Android版に必要な対応 |
| --- | --- | --- |
| Androidプロジェクト | リポジトリに存在しない | 独立した`android/`プロジェクトを作る |
| 認証 | WebはBetter AuthのCookieセッション。Android向け方式は未採用 | Androidからの認証方式、失効、端末内保存を決める |
| API | 認証と保存企業のRoute Handlerがある | プロフィール、診断、提案、企業詳細、企業情報の共通APIを定義・実装する |
| プロフィール・企業デモデータ | Web画面ではブラウザーのローカル保存領域を使用 | Androidから使うデータの保存先と本人確認を決める |
| 診断回答・提案 | Web画面とセッション保存領域で処理 | 質問ID・1〜5の回答をAPIへ送り、診断IDで結果を取得する |
| 画面デザイン | Web画面と共通色の定義がある | Composeのテーマと部品に移し、画面ごとの独自値を増やさない |

上の表は着手前の記録であり、現在の実装状態を示すものではない。現在は `android/`、`docs/android-api-v1.md`、`web/src/app/api/v1/` を参照する。

### 現在の進捗

- Android 8.0（API 26）以降のComposeアプリを作成し、デバッグビルドとエミュレーター起動を確認した。
- 署名付きBearerと架空メールによる認証、希望条件、12問の診断、提案結果、企業詳細、保存企業一覧のJSON APIを実装した。AndroidはMySQLへ直接接続しない。
- 企業詳細の未確認項目・出典・確認日・応募先は、確認できない場合に `null` と表示上の「未確認」「なし」で扱う。
- 企業アカウントの承認、実在企業情報、業界の提案、実機での確認は未達。学生プロフィール全項目のAPI保存は確認済みで、エミュレーター画面での保存・再表示は未確認。Androidの再起動後のログイン復元、ログアウト後の非復元、失効済みトークンの削除はエミュレーターで確認済み。FR-01〜FR-09の受入完了は未判定。

## 3. 実装前に決めること

1. **対象端末**：最低Androidバージョン、対象画面サイズ、実機・エミュレーターの確認範囲（TBD-09）。
2. **認証**：Webと共通の利用者IDを使う方法、Android用のセッションまたはトークン、ログアウト・失効・安全な保存方法（TBD-08）。Bearer方式は現時点では採用案にとどめる。
3. **API契約**：各操作のURL、HTTPメソッド、入力・出力、エラー形式、診断IDと企業IDの扱い。WebとAndroidが同じ仕様書を参照する。
4. **保存と権限**：プロフィール、診断、保存企業、企業情報の保存先。学生本人と企業担当者の権限をAPIで検証する方法（TBD-02、TBD-06、TBD-08）。
5. **判定ルール**：希望条件、質問・企業評価、同点順位、未確認値の扱いを確定する（TBD-02〜04、TBD-07）。
6. **企業情報の確認**：出典、確認日、公式応募先、登録・更新・公開の責任者を決める（TBD-06、TBD-07）。

未確定事項を仮の本番仕様として固定しない。決定が必要な機能に着手する前に担当者・チームで合意し、要件定義とAPI仕様へ反映する。

## 4. 開発順序と完了条件

### 第1段階：共通仕様とWeb/APIの準備

- FR-01〜FR-09の入力・出力・エラー・権限をAPI仕様書に記載する。
- プロフィール、企業情報、診断実行、診断IDによる結果、企業IDと診断IDによる詳細、保存企業のAPIをWeb側に実装する。
- 0社なら正常な空一覧を返す。最低条件を先に判定し、未確認値を0や空文字で代用しない。
- APIで本人または自社のデータだけを読み書きできることをテストする。

**完了条件**：架空データでWebから入力〜詳細確認までをAPI経由で通せる。Androidがブラウザー保存データに依存せず同じ結果を取得できる。

### 第2段階：Androidプロジェクトの作成

- `android/`配下にAndroid Studio用プロジェクトを作る。Kotlin、Jetpack Compose、Material 3を基本とし、API通信には技術選定案のKtor Clientを検討する。
- SDK、Gradle、依存関係のバージョンは着手時に公式互換表とローカル環境を確認して固定する。生成物・キャッシュ・ローカル設定は`android/.gitignore`で管理外にする。
- 共通デザイントークン、文字サイズ、余白、タッチ領域をComposeテーマと共通部品にまとめる。

**完了条件**：Android Studioで同期・デバッグビルドが通り、エミュレーターで起動する。

### 第3段階：学生の基本操作

- ログイン・新規登録後にホームを表示し、ログアウト時はログイン画面へ戻す。
- プロフィールと希望条件をAPIへ保存・再表示する。月給は画面では万円で入力し、APIの単位は契約で明記する。
- 学生向けボトムナビゲーションは「ホーム」「プロフィール」「提案企業」とする。診断入力と企業詳細は含めない。

**完了条件**：ログイン状態と本人のプロフィールが再起動後も仕様どおり復元され、別利用者の情報を表示しない。

### 第4段階：診断と提案

- 1〜5の回答を質問IDとともに送信し、診断IDで提案結果を取得する。
- 候補0社、1社、2社を表示する。0社の場合は診断の再実施と希望条件の再設定をそれぞれ選べるようにする。
- 企業詳細には企業IDと診断IDを渡し、同じ診断の提案理由、未確認事項、出典・確認日、公式応募先を表示する。
- 飲み会、新卒配属、転勤、リモート、有給、休日連絡、社内イベント、3年以内離職率、新卒がギャップを感じやすい点を企業詳細で表示する。保存企業一覧からも詳細を開けるようにする。

**完了条件**：WebとAndroidで同じ回答・条件に対する提案企業と理由が一致する。公式応募先URLがない場合は応募リンクを表示しない。

### 第5段階：企業向け機能と最終確認

- 企業アカウントの承認・権限・公開手順が決まった後、自社情報だけを登録・編集できる画面を作る。
- FR-01〜FR-09、NFR-01〜NFR-03の受入条件を、APIテスト、Compose UIテスト、実機またはエミュレーターの操作で確認する。
- 小画面、文字拡大、通信失敗、セッション失効、0社・1社・2社、未確認値、条件の変更を確認する。

**完了条件**：要件定義の受入条件と実測結果を対応づけ、未達項目を明示できる。

## 5. 画面と操作の設計基準

- 一画面に役割を詰め込まず、ホーム→診断→結果→詳細の順に必要な情報を示す（SHIG 82）。
- 現在地とホームへ戻る経路を一貫して示す（SHIG 59・60）。
- ボタンは指で押しやすい大きさと間隔を確保し、実機で確認する（SHIG 78）。
- 保存・送信の成功と失敗を操作箇所の近くで明示し、エラーを黙って既定値に置き換えない。

## 6. 変更範囲と着手条件

Android版の主な作成先は`android/`とする。Web/APIや共通仕様の変更は担当者と範囲を調整してから行う。現存するWeb側の未コミット変更を上書きしない。依存関係や認証方式の採用、API契約、スキーマ変更は別の判断としてレビューする。

この文書は当初計画と現在の進捗を併記する。未達項目の受入条件は `docs/requirements.md` に従う。
