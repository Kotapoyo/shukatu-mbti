# 企業MBTI 要件定義書

- 作成日：2026年10月7日
- 状態：初版・チーム確認用
- 基準資料：[README.md](../README.md)

## 1. 目的と位置づけ

企業MBTIは、就活の手間を減らしたい新卒学生と、人手の確保を優先する企業を引き合わせる、モバイル対応の就活アプリです。

学生の最低限の希望条件と企業の募集条件を照合し、条件を満たす求人から、性格傾向と企業の働き方・職場特性に合う業界や企業を提案します。学生の企業探し・比較・応募までの負担軽減、企業と学生の接点の拡大、人手不足の改善、双方の認識のずれの軽減を目指します。

本書はREADMEの開発予定を要件として整理したものです。実装済みであることや、チーム内で承認済みであることを示すものではありません。READMEで決まっていない仕様は「未定」とし、実装前に合意が必要な事項として管理します。

## 2. 対象ユーザーと開発体制

| 対象 | 利用目的 |
| --- | --- |
| 新卒学生 | 希望条件と性格傾向に合う業界・企業を見つけ、公式応募先へ進む |
| 企業 | 自社の働き方・福利厚生を登録し、募集条件に合う学生との接点を得る |

企画・開発はチーム児玉（児玉・松本・田代・村田）の4名で行います。企画、画面、診断処理、企業情報を分担する予定です。各担当者の割り当てと予算は未定です。

## 3. 開発範囲

### 3.1 初期開発の予定範囲

- 学生のプロフィール・最低限の希望条件の登録
- 企業による働き方・福利厚生の登録
- 希望条件による求人の絞り込み
- 短い質問による性格傾向の把握と企業の職場特性との照合
- 業界と企業1〜2社の提案
- 企業詳細・診断理由・未確認事項・出典・確認日の表示
- 公式応募先URLの表示
- 該当する求人がない場合の希望条件の再設定
- サブスクリプション登録企業の優先表示
- スマートフォンでの入力・結果確認

サブスクリプションの料金・契約期間・決済方法は未定です。優先表示を実現するための登録状態の管理方法と、課金機能を初期開発に含める範囲も決定が必要です。

### 3.2 追加候補と対象外

地域の詳細検索、口コミ、履歴書・選考状況の管理は追加候補です。初期開発に含めるかは未定であり、採用を決めるまで必須の完成条件には含めません。

性格診断による能力や採用可否の断定は対象外です。応募は公式応募先URLへの案内を予定し、アプリ内での応募受付や選考処理の要否は未定です。

## 4. 想定する利用の流れ

画面構成と操作順序の詳細は未定です。以下は、READMEの機能をつなげた想定の流れです。

### 4.1 学生

1. プロフィールと最低限の希望条件を登録する。
2. 短い質問に回答する。
3. 希望条件を満たす求人から、性格傾向に合う業界と企業の提案を受ける。
4. 企業詳細、診断理由、未確認事項、出典・確認日を確認する。
5. 希望する企業の公式応募先URLへ進む。
6. 該当する求人がない場合は、本人が希望条件を変更して再度候補を確認する。

### 4.2 企業

1. 自社の働き方・福利厚生を登録する。
2. 登録した情報が求人の絞り込み・職場特性の照合・企業詳細に利用される。
3. サブスクリプションに登録した場合は、最低条件を満たす候補の表示で優先表示の対象となる。

企業の認証方法、登録情報の確認・公開手順、契約手続きは未定です。

## 5. 機能要件と受入条件

以下の受入条件は、各機能が完成したかを確認するための条件です。判定基準などが未定の機能は、その仕様を確定した後に具体的なテストデータを用意します。

| ID | 機能要件 | 受入条件 |
| --- | --- | --- |
| FR-01 | 学生がプロフィールと最低限の希望条件を登録できる | 登録した希望条件が求人の絞り込みに反映される |
| FR-02 | 企業が自社の働き方・福利厚生を登録できる | 登録内容を確認でき、企業詳細などに反映される |
| FR-03 | 地域、給与、休日、福利厚生などで求人を絞り込める | 確定した条件判定ルールに従い、最低条件を満たす求人が候補になる |
| FR-04 | 短い質問への回答から性格傾向を把握し、企業の働き方・職場特性と照合する | 確定した質問・判定基準に従って回答が診断結果に反映される |
| FR-05 | 最低条件を満たす求人から、傾向に合う業界と企業1〜2社を提案する | 候補がある場合、条件を満たす企業が1〜2社と関連する業界が表示される |
| FR-06 | 企業詳細と診断理由を表示する | 提案された企業の詳細と、確定した判定基準に基づく理由を確認できる |
| FR-07 | 未確認事項、企業情報の出典・確認日を表示する | 未確認の項目を確認済みと誤認させず、出典・確認日を確認できる |
| FR-08 | 公式応募先URLを表示する | URLがある企業について公式応募先へ移動できる |
| FR-09 | 該当する求人がない場合、学生本人が希望条件を再設定できる | 該当なしが分かり、本人の変更後の条件で候補が再判定される |
| FR-10 | サブスクリプション登録企業を上位に表示する | 最低条件を満たす候補内で、確定した順位ルールに従って優先表示される |

## 6. 絞り込み・診断・表示のルール

### 6.1 最低条件の優先

勤務地・給与などの最低条件を、性格傾向との相性やサブスクリプションによる優先表示より優先します。最低条件を満たさない求人を、優先表示だけを理由に提案対象に含めません。

条件の必須・任意区分、給与や休日の比較単位、地域の指定方法、複数条件の組み合わせ方法は未定です。

### 6.2 診断と提案

短い質問によって性格傾向を把握し、企業の働き方・職場特性と照合します。性格診断は企業選びの参考として扱い、能力や採用可否を断定しません。

質問数、設問、回答形式、採点方法、業界・企業との対応づけ、同点の場合の扱い、候補が1社の場合の表示方法は未定です。

### 6.3 サブスクリプションによる優先表示

サブスクリプション登録企業を上位に表示します。この処理は最低条件を満たす候補に対して適用します。

性格傾向との相性と契約状態をどの順序で順位に反映するか、複数の契約企業の順位、表示枠、契約の有効性の判定、契約終了時の扱いは未定です。契約状態のみで相性を断定しないよう、診断理由との整合を確認します。

### 6.4 情報不足と該当なし

未確認の情報は、未確認であることを明示します。最低条件に関する情報が不足した求人を候補に含めるかは未定です。情報不足を「条件を満たしている」と扱う仕様にはしません。

該当する求人がない場合、学生本人が条件を再設定します。システムが本人の操作なしに最低条件を緩和することは想定しません。

出典・確認日や公式応募先URLがない場合の表示・候補への採用可否は未定です。

以下は機能に必要な情報の分類であり、確定したDB設計ではありません。詳細な項目名、型、必須項目、入力制約、保存期間は別途決定します。

## 8. 非機能要件と運用

| ID | 項目 | 要件・状態 |
| --- | --- | --- |
| NFR-01 | モバイル対応 | スマートフォンでプロフィール・希望条件の入力、質問への回答、企業詳細・結果の確認ができる。対象端末・ブラウザ・画面サイズは未定 |
| NFR-02 | 秘密情報の管理 | APIキーやパスワードなどの秘密情報をREADMEやリポジトリに登録しない。環境変数の設定例には変数名と用途を記載する |
| NFR-03 | 情報の更新 | 企業の募集条件・採用予定人数・職場特性を収集・更新する。取得元、更新頻度、担当者、失敗時の対応は未定 |

個人情報の閲覧権限、認証、保存・削除、同意の取得方法は未定です。また、応答時間、想定利用者数、可用性、バックアップ、監視、アクセシビリティの具体的な目標も未定です。運用開始までに必要な条件を決定します。

言語・フレームワーク、フロントエンド、バックエンド、DB、実行・公開環境は未定です。環境構築・起動・テスト・lint・ビルドのコマンドは、技術選定と実装後にREADMEへ記載します。

## 9. 確認方法と完成の判断

FR-01〜FR-10とNFR-01〜NFR-03を、確定した仕様とテストデータに基づいて確認します。初期開発の範囲を変更する場合は、本書の開発範囲・要件・受入条件を併せて更新します。

特に次のケースを確認します。

- 希望条件を満たす求人と満たさない求人が混在している場合
- 候補が0社、1社、2社以上の場合
- 条件を満たす契約企業と非契約企業が混在している場合
- 契約企業が最低条件を満たさない場合
- 診断に対する回答が異なる場合
- 企業情報に未確認項目がある場合
- 条件を再設定した場合
- スマートフォンで入力から結果確認・応募先への移動まで行う場合

判定基準や情報不足の扱いが未定のまま、該当機能の受入完了とはしません。テスト・lint・ビルドの具体的な実行方法は、選定した技術に合わせて定めます。
