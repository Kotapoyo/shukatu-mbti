# 企業MBTI

## 概要

企業MBTIは、就活の手間を減らしたい新卒学生と、人手の確保を優先する企業を引き合わせる、モバイル対応の就活アプリです。

学生の最低限の希望条件と企業の募集条件を照合し、条件を満たす求人から、性格傾向と企業の働き方・職場特性に合う業界や企業を提案します。学生の企業探し・比較・応募までの負担を減らし、企業には募集条件に合う学生との接点を提供することで、人手不足の改善を目指します。また、双方の条件や働き方に関する認識のずれを軽減します。

現在は開発用の画面と機能を作成している段階です。この `murata` ブランチにはホーム、学生プロフィール、企業情報登録、保存企業、診断、提案結果の画面があります。架空学生の登録・ログイン、診断回答に応じた架空企業の提案、本人用の企業保存・一覧表示を試せます。実際の求人データによる提案は完成していません。

- 対象：就活を面倒に感じる新卒学生、人手の確保を優先する企業
- 企画・開発体制：チーム児玉（児玉・松本・田代・村田の4名）
- 担当：田代がログイン・新規登録と認証、児玉が学生プロフィール、幸太郎が診断・提案結果・企業詳細、村田がホーム・企業情報登録と共通UI。共通API仕様は幸太郎が取りまとめます。
- 予算：未定。開発・サーバー・データ取得・配信にかかる費用を算定予定

## 主な機能

- **プロフィール・希望条件の登録**：学生のプロフィールと最低限の希望条件を登録する。
- **企業による情報登録**：企業が自社の働き方・福利厚生を登録できるようにする。
- **求人の絞り込み**：地域、給与、休日、福利厚生などの条件で求人を絞り込む。
- **性格傾向と職場特性の照合**：短い質問から性格傾向を把握し、企業の働き方・職場特性と照合する。
- **業界・企業の提案**：最低条件を満たす求人から、傾向に合う業界と企業1〜2社を提案する。
- **企業詳細・提案理由の表示**：企業情報、診断理由、未確認事項、情報の出典・確認日を表示する。
- **応募先への案内**：公式応募先URLを表示する。
- **該当する求人がない場合の対応**：学生本人が希望条件を再設定できるようにする。

勤務地・給与などの求人の最低条件を先に判定します。診断は1〜5の5段階で回答し、対応する企業の働き方の評価との差が小さい企業を上位にして、条件を満たす候補から1〜2社を提案します。具体的な設問、評価項目との対応、同点時の順位は未定です。サブスクリプションによる優先表示と課金機能は採用しません。性格診断は企業選びの参考として扱い、能力や採用可否を断定する用途は対象外とします。

不明な値は `null` と「未確認」で扱い、最低条件や診断の照合に必要な情報が未確認の企業は提案候補から除外します。それ以外の未確認項目は企業詳細に表示します。出典URL・確認日がなければ「なし」と表示し、企業の自己申告だけでは確認済みにしません。公式応募先URLがない場合は応募リンクを表示しません。

現在の画面デモでは、ログイン中の利用者がブラウザー内に登録したデモ企業と、コードに用意した架空企業を候補にします。プロフィールを保存している場合は、希望勤務地と最低月給を先に判定し、不一致または必要な値が不明の企業を除外します。休日・福利厚生の最低条件判定は未実装です。12問のうち通勤距離は点差に含めず、残り11問について回答値と企業評価値の差の絶対値を合計します。合計が小さい順に2社を表示し、同点時は既存の架空企業、登録したデモ企業の順とします。条件を満たす企業が0社なら空の結果を表示し、プロフィール変更後に同じ診断回答で再判定できます。このデモ用判定を実際の求人に適用する前に、チームで正式な評価項目と条件を確定します。

学生はメールアドレスとパスワードで登録・ログインします。開発用の Web 認証には Better Auth を採用しました。企業アカウントの一般向け新規登録は設けず、開発中は運営側が作成時に承認した企業・担当者をダミーデータとして用意します。学生は本人の情報、企業担当者は自社の情報だけを操作できるよう、APIでも権限を確認します。実在する企業の承認基準、実在する学生情報の保存・削除・同意は未定です。

地域の詳細検索、口コミ、履歴書・選考状況の管理は追加候補です。初期開発に含めるかは未定です。

## 技術構成

開発用 Web 認証には Better Auth とローカル MySQL を採用しました。その他は要件定義書をもとにした技術選定案であり、チームの合意後に実装へ進みます。

| 項目 | 内容 |
| --- | --- |
| Web版 | TypeScript、Next.js App Router |
| Androidアプリ | Web版の開発完了後、Android Studio と Kotlin、Jetpack Compose で実装 |
| Android API通信 | Ktor Client |
| Web画面・デザイン | Tailwind CSS、shadcn/ui。共通テーマと共通部品を使う |
| Android画面・デザイン | Jetpack Compose、Material 3。Web版と共通の色、文字、余白などのデザイン基準に合わせる |
| バックエンド・API | Next.js Route Handlers（TypeScript）。診断・絞り込み・提案を共通JSON APIとして実装し、Web版とAndroidアプリから利用 |
| データベース | 認証にはローカル MySQL と mysql2 を使用。開発PCには MySQL 8.0 がインストール済み。8.4 LTS への統一と独立した Kysely 導入は採用案 |
| 認証 | WebはBetter AuthのCookieセッションとMySQLを採用。AndroidのBearerトークンは後続の採用案 |
| 企業・求人情報の取得方法 | 初期段階は確認済み情報を管理者が登録。出典URLと確認日を保存し、自動取得は情報源と更新方法の合意後に判断 |
| 実行環境 | Web/APIとMySQLは各自のPCでローカル実行。デモはダミーデータを使用し、現時点でクラウドは使わない |
| API・秘密情報 | APIの入出力仕様を共通資料で管理する。MySQLの接続情報はサーバー環境にだけ置き、Web・AndroidアプリからDBへ直接接続しない |
| テスト | API・判定ロジックの自動テストとPlaywrightでWeb操作を確認。Android実装時は Compose のUIテストを追加 |

まずWeb版を完成させ、その後Androidアプリを作ります。診断や求人提案の処理は Next.js のサーバーAPIに集め、両方の画面で同じAPIを使います。診断時は質問IDと1〜5の回答を送り、診断IDで提案結果を取得します。企業詳細には企業IDと診断IDを渡し、同じ診断の提案理由を表示します。候補が0社なら正常な空一覧を返します。具体的なAPIのURLと項目名は未定です。画面側へ判定ロジックを重複実装しません。認証データには MySQL を使います。学生プロフィール、企業、求人、希望条件の保存設計と独立したKysely導入は採用案です。

Web版とAndroidアプリでは画面部品が異なるため、色、文字、余白、ボタンなどの共通デザイン基準を先に決め、それぞれのUI部品へ反映します。Web版は Tailwind CSS のテーマと shadcn/ui、Androidアプリは Material 3 を使います。

Webの認証には Better Auth を採用し、Cookieセッションと認証データをMySQLに保存します。AndroidのBearerトークン対応は後続の案で、実装していません。個人情報の項目、閲覧権限、保存・削除、同意の取り方は未決です。これらを決めるまでは実在する学生情報を保存せず、ダミーデータで開発します。課金・決済機能は実装しません。

## 起動方法

以下は Windows の PowerShell と MySQL Workbench で、初めてローカル環境を用意する手順です。Node.js・npm と MySQL 8.0 を先にインストールし、MySQL サーバーを起動してください。コマンドは、特記がない限りリポジトリのルートで実行します。

ホーム中央の「診断を始める」から診断画面へ進めます。12問に回答して内容を確認すると、架空企業の提案結果を表示できます。回答はブラウザーのタブ内に一時保存され、DBには保存されません。ログイン中はプロフィール画面で希望勤務地と最低月給を保存でき、企業情報登録画面で11項目の5段階評価を持つデモ企業を登録・編集できます。プロフィールとデモ企業は利用者IDごとに同じブラウザーのローカル保存領域へ保存し、他の端末には共有しません。既存の架空企業を保存する際は、診断回答と勤務地・最低月給だけをAPIへ送り、保存対象を再判定します。提案結果の「この企業を保存」から本人の企業リストへ保存できます。既存の架空企業の保存先はMySQL、画面から登録したデモ企業の保存先はブラウザーです。学生向けボトムバーの「プロフィール」から入力画面へ、「提案企業」から保存企業一覧へ進めます。ログイン・新規登録は Better Auth の認証APIからローカル MySQL に保存します。開発中の登録は `@example.com` の架空メールだけ受け付けます。実際の企業情報の登録と求人データによる提案は準備中です。

### 開発用の認証・MySQL 設定

1. MySQL Workbench でローカル MySQL に管理者として接続し、[`web/db/create-database.sql`](web/db/create-database.sql) を開いて実行します。続いて以下のSQLを実行します。`<ローカル専用の強いパスワード>` は実行前に自分で生成した値へ置き換えてください。既にアプリ専用ユーザーを作成済みなら、この作成手順は繰り返さないでください。

   ```sql
   CREATE USER 'shukatu_app'@'127.0.0.1' IDENTIFIED BY '<ローカル専用の強いパスワード>';
   GRANT ALL PRIVILEGES ON shukatu_mbti.* TO 'shukatu_app'@'127.0.0.1';
   ```

2. PowerShell で環境変数ファイルを作成します。

   ```powershell
   Copy-Item .\web\.env.example .\web\.env.local
   ```

   `web/.env.local` の `MYSQL_USER` を `shukatu_app` に、`MYSQL_PASSWORD` を手順1の値に設定します。`MYSQL_HOST=127.0.0.1`、`MYSQL_PORT=3306`、`MYSQL_DATABASE=shukatu_mbti` はMySQLの実際の設定に合わせます。`BETTER_AUTH_SECRET` は32文字以上のランダムな値に置き換えます。`BETTER_AUTH_URL` は起動するURLと完全に合わせ、既定の `http://localhost:3000` からポートを変える場合は両方を変更します。`.env.local` は Git 管理外です。

3. PowerShell で依存関係を導入し、Better Auth の認証用テーブルを作成します。マイグレーションの確認が表示されたら、内容を確認して実行します。

   ```powershell
   Set-Location .\web
   npm.cmd ci
   npx.cmd auth@1.7.14 migrate --config .\src\lib\auth.ts
   ```

4. MySQL Workbench でアプリ専用ユーザーの接続を開き、`shukatu_mbti` を既定のスキーマに選択してから、[`web/db/001_saved_company.sql`](web/db/001_saved_company.sql) を開いて実行します。これは `user` テーブルを参照するため、手順3の後に初回だけ実行します。`SHOW TABLES;` で `user`、`session`、`account`、`verification`、`saved_company` を確認します。

5. `web/` の PowerShell で起動します。ブラウザーで `http://localhost:3000` を開き、`student@example.com` のような未使用の架空メールと開発専用パスワードで新規登録します。実在の氏名、メールアドレス、使い回しのパスワードは入力しないでください。

   ```powershell
   npm.cmd run dev
   ```

   ポートを変更するときは `npm.cmd run dev -- --port 3001` のように起動し、手順2の `BETTER_AUTH_URL` も同じポートへ変更してください。登録に失敗したら、MySQLの起動、接続情報、テーブル、URLとポートの一致を確認します。

認証用の `user`、`session`、`account`、`verification` テーブルは Better Auth の CLI が管理します。`saved_company` はログイン中の学生IDと既存の架空企業IDを保存し、同じ企業の重複を防ぎます。プロフィールはブラウザーで利用者IDごとに保存し、診断回答は同じタブのセッション内に保存します。どちらもDBには保存しません。実在利用者の登録、企業アカウント、メール確認、パスワード再設定、個人情報の保存・削除は別途仕様を決めてから対応します。
