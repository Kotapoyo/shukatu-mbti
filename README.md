# 企業MBTI

## 概要

企業MBTIは、就活の手間を減らしたい新卒学生と、人手の確保を優先する企業を引き合わせる、モバイル対応の就活アプリです。

学生の最低限の希望条件と企業の募集条件を照合し、条件を満たす求人から、性格傾向と企業の働き方・職場特性に合う業界や企業を提案します。学生の企業探し・比較・応募までの負担を減らし、企業には募集条件に合う学生との接点を提供することで、人手不足の改善を目指します。また、双方の条件や働き方に関する認識のずれを軽減します。

現在は企画段階です。以下の機能は開発予定であり、実装済み機能を示すものではありません。

- 対象：就活を面倒に感じる新卒学生、人手の確保を優先する企業
- 企画・開発体制：チーム児玉（児玉・松本・田代・村田の4名）
- 分担する領域：企画、画面、診断処理、企業情報。担当者の割り当ては未定
- 予算：未定。開発・サーバー・データ取得・配信にかかる費用を算定予定

## 主な機能

- **プロフィール・希望条件の登録**：学生のプロフィールと最低限の希望条件を登録する。
- **企業による情報登録**：企業が自社の働き方・福利厚生を登録できるようにする。
- **サブスクリプション登録企業の優先表示**：サブスクリプションに登録した企業を上位に表示する。
- **求人の絞り込み**：地域、給与、休日、福利厚生などの条件で求人を絞り込む。
- **性格傾向と職場特性の照合**：短い質問から性格傾向を把握し、企業の働き方・職場特性と照合する。
- **業界・企業の提案**：最低条件を満たす求人から、傾向に合う業界と企業1〜2社を提案する。
- **企業詳細・提案理由の表示**：企業情報、診断理由、未確認事項、情報の出典・確認日を表示する。
- **応募先への案内**：公式応募先URLを表示する。
- **該当する求人がない場合の対応**：学生本人が希望条件を再設定できるようにする。

勤務地・給与などの最低条件を優先し、未確認の項目は明示します。サブスクリプション登録企業の優先表示は、この最低条件を優先する方針に沿って設計します。具体的な表示順位の決め方や、性格傾向との相性を順位に反映する方法は未定です。サブスクリプションの料金・契約期間・決済方法は未定です。性格診断は企業選びの参考として扱い、能力や採用可否を断定する用途は対象外とします。

地域の詳細検索、口コミ、履歴書・選考状況の管理は追加候補です。初期開発に含めるかは未定です。

## 技術構成

データベースはMySQLを使う方針です。その他は要件定義書をもとにした技術選定案なので、チームの合意後に実装へ進みます。具体的なバージョンは開発環境を作る時点で決め、依存関係ファイルで固定します。

| 項目 | 内容 |
| --- | --- |
| Web版 | TypeScript、Next.js App Router |
| Androidアプリ | Web版の開発完了後、Android Studio と Kotlin、Jetpack Compose で実装 |
| Android API通信 | Ktor Client |
| Web画面・デザイン | Tailwind CSS、shadcn/ui。共通テーマと共通部品を使う |
| Android画面・デザイン | Jetpack Compose、Material 3。Web版と共通の色、文字、余白などのデザイン基準に合わせる |
| バックエンド・API | Next.js Route Handlers（TypeScript）。診断・絞り込み・提案を共通JSON APIとして実装し、Web版とAndroidアプリから利用 |
| データベース | MySQL 8.4 LTS、Kysely、mysql2。提供元は未定 |
| 認証 | Better Authを採用案とする。WebはCookieセッション、Androidは署名必須のBearerトークンを使い、認証データはMySQLに保存 |
| 企業・求人情報の取得方法 | 初期段階は確認済み情報を管理者が登録。出典URLと確認日を保存し、自動取得は情報源と更新方法の合意後に判断 |
| 実行環境 | Web/APIとMySQLは各自のPCでローカル実行。デモはダミーデータを使用し、現時点でクラウドは使わない |
| API・秘密情報 | APIの入出力仕様を共通資料で管理する。MySQLの接続情報はサーバー環境にだけ置き、Web・AndroidアプリからDBへ直接接続しない |
| テスト | API・判定ロジックの自動テストとPlaywrightでWeb操作を確認。Android実装時は Compose のUIテストを追加 |

まずWeb版を完成させ、その後Androidアプリを作ります。診断や求人提案の処理は Next.js のサーバーAPIに集め、両方の画面で同じAPIを使います。APIの仕様を共通資料で先に合意し、画面側へ判定ロジックを重複実装しません。学生、企業、求人、希望条件とBetter Authの認証データは MySQL で管理します。KyselyはTypeScriptでSQLに近い問い合わせを書き、型で間違いを見つけやすくするために選びます。

Web版とAndroidアプリでは画面部品が異なるため、色、文字、余白、ボタンなどの共通デザイン基準を先に決め、それぞれのUI部品へ反映します。Web版は Tailwind CSS のテーマと shadcn/ui、Androidアプリは Material 3 を使います。

認証ライブラリはBetter Authを採用案とします。WebはCookieセッション、AndroidはBearerトークンで同じ認証基盤を使います。Androidのトークンは端末の安全な領域に保管し、Bearerプラグインの署名検証を必須にします。個人情報の項目、閲覧権限、保存・削除、同意の取り方は未決です。これらを決めるまでは実在する学生情報を保存せず、ダミーデータで開発します。課金機能も初期開発に含めるか未定のため、決済連携は選定対象に含めません。

## テスト・確認方法

テストツールの案は「技術構成」に記載しています。lint・ビルドを含む実行コマンドは、チーム合意後に追記します。開発時には、以下の動作を確認します。

- プロフィール・希望条件を登録し、求人の絞り込みに反映できること
- 企業が自社の働き方・福利厚生を登録できること
- 最低条件を満たす求人から企業が提案されること
- 最低条件を満たす候補の表示で、サブスクリプション登録企業の優先表示が反映されること
- 質問への回答に応じた診断結果と、提案理由が表示されること
- 企業情報の出典・確認日と、未確認事項が表示されること
- 該当する求人がない場合、本人が希望条件を再設定できること
- 公式応募先URLが表示され、リンク先へ移動できること
- スマートフォンで入力や結果の確認ができること

## 開発ルール

企画書ではGitHubの運用ルールが未定のため、以下はチームで確認するための案です。

- 作業内容と完了条件をIssueに記載する。
- 作業ごとにブランチを作成する。命名例：`feature/機能名`、`fix/修正内容`、`docs/資料名`。
- 変更はPull Requestで共有し、変更内容・確認結果・関連Issueを記載する。
- 他のメンバーによるレビュー後にマージする。
- コードや仕様の変更に合わせて、READMEや関連資料も更新する。

ブランチ名、レビュー人数、マージ方法、各領域の担当者は、チーム内で合意後に確定します。
